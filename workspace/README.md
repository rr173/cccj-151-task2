# 山火应急撤离编排系统

指挥员导入受威胁网格、道路通行状态、避难点床位与可用车辆，登记每户人数、行动辅助需求、
宠物与联络方式；系统把**家庭作为不可拆分单元**分配到避难点与撤离批次，在满足床位、
车辆座位、无障碍、道路容量与避难点接收条件的前提下，给出可比较的候选方案并发布分区撤离令。

- **零第三方依赖**：后端仅用 Python 3.9+ 标准库（`http.server` + `sqlite3`），前端为原生 HTML/JS。
- **持久化**：SQLite（WAL）。进程/容器重启后，已发布命令、出发记录、剩余容量自动恢复。
- **承诺不可变**：车辆点击「离场」后，该批次与目的地床位占用立即锁定，之后重新规划
  不会改派已出发家庭，也不会释放其床位。
- **事件驱动重算**：火线扩大、道路封闭、车辆故障、避难点暂停时，只撤回/重算**未出发**批次，
  并对无法安置的家庭逐条说明阻断约束；资源恢复后可继续编排。
- **乐观并发发布**：方案携带制定时修订号；多名指挥员基于旧方案同时发布时只有第一份生效，
  其余返回 409，强制基于最新态势重新规划。

## 快速开始

### 方式一：容器（推荐）

```bash
docker compose up -d --build
# 打开 http://localhost:8080
docker compose logs -f
```

数据保存在命名卷 `evac-data` 中；容器重启后命令与承诺完整恢复。

### 方式二：本地直接运行

```bash
./run.sh                 # 或：python3 backend/server.py
# 打开 http://localhost:8080
```

可选环境变量：`EVAC_PORT`（默认 8080）、`EVAC_DB`（默认 ./data/evac.db）、
`EVAC_NO_SEED=1`（关闭演示数据播种）。

### 重置/重建演示数据

```bash
python3 seed_demo.py --reset
```

## 演示推演流程（约 3 分钟）

1. 打开**作战地图**：6 个网格、11 条道路（r2 为容量瓶颈）、4 个避难点（S4 暂停接收）、
   5 辆车、11 户受威胁家庭。
2. 进入**方案比较与发布** → 填写指挥员代号 →「生成候选方案」。可多生成几个方案比较
   波次数、车辆数、床位预测；查看拼车、无障碍车（V3/V4）与宠物户（去 S1/S3 而非禁宠的 S2）。
3. 点击**发布分区撤离令**；再用同一旧方案点发布会被 409 拒绝（乐观并发）。
4. 到**撤离批次**页，对第 1 波某车点「确认车辆离场」——批次变红成为承诺，
   同车后续波次自动撤回待重排。
5. 回地图**点击道路 r5 封闭**（或用右侧态势面板封路/车辆故障/暂停避难点/火线扩大到 G4）：
   只有受影响的未出发批次被撤回；已出发批次和已承诺床位不变。
6. 再「生成候选方案」：系统只安置剩余家庭；若不可行，每户列出具体约束；
   恢复道路/车辆/避难点后方案重新可行。
7. 重启服务（或重启容器），刷新页面：命令、出发记录、剩余容量全部恢复。

## 页面

- **作战地图**：SVG 可点击地图，道路点按即封闭/恢复，批次路线按波次着色
  （实线=已离场承诺，虚线=待出发），实时显示床位占用与待撤离户数。
- **撤离批次**：按波次查看批次、车辆、路线、搭载家庭；确认离场形成承诺。
- **方案比较与发布**：候选方案卡片（可行性、波次、批次、车辆、是否过期），
  详情含每户不可行原因与床位预测，一键发布。
- **资源与导入**：JSON 批量导入网格/道路/避难点/车辆（同 code 幂等覆盖）。
- **受威胁住户**：表单登记人数、行动辅助、宠物、联络；同户号重复导入自动忽略。
- **事件日志**：所有导入、发布、离场、封路/恢复等审计记录（含修订号）。

## 规划模型

- 路径：仅开放道路组成无向图，Dijkstra 最短路 + 逐边删除生成最多 3 条备选路径。
- 批次：一辆车 + 一个出发网格 + 一个目的地避难点 + 一条路径；
  同网格同目的地家庭在座位与无障碍属性允许时合乘。
- 搜索：按「最小波次数」目标，K=1..N 逐次加深的 DFS 回溯，
  约束包括床位、座位、无障碍、宠物、道路单波次容量、车辆每波次一趟。
- 安全网：发布前 `validate_plan` 独立复核全部硬约束（路径连续性/封闭边、
  床位、座位、容量、重复分配、重派已出发户等）。
- 诊断：无解时先做「放宽道路时序」的贪心试分配，区分单户硬阻断（封路、无障碍车、
  接收条件、确定性床位不足）与多户竞争瓶颈（床位在竞争中耗尽、车辆同时性不足）。

## 并发与一致性说明

- 所有「读-改-写」在单进程 `RLock` 内串行，SQLite WAL 保证崩溃一致性。
- `revision` 在每次资源变化/发布/离场时递增；方案记录 `base_revision`。
- 发布是 compare-and-swap：`base_revision == 当前 revision` 才允许，
  因此并发发布天然只有一份生效。
